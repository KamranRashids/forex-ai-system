# Phase 10 — F-07: Reproducible Python dependency locks (pip-tools + hashes)

**Status: RESOLVED — implemented and verified 2026-09-12.**

Closes finding **F-07** of `docs/dependency-security-audit.md` (§7): the backend
was installable only from `pyproject.toml` **version ranges**, so every fresh
install (Docker build, CI, host venv) **re-resolved versions from PyPI at that
moment** and could silently drift apart from the locally validated environment.
This document records the mechanism chosen, the wiring, and the verification
evidence for the lock-enabled, hash-checked, reproducible install path.

---

## 1. Objective

Make every Python install of `backend/` **reproducible and tamper-evident**:

1. versions are **exactly pinned** (not range-resolved) at install time;
2. every downloaded artifact is **verified against SHA-256 hashes**
   (`pip --require-hashes`);
3. Docker images, CI, and the host dev venv all install from the **same locked
   closure**, proving a clean install reproduces the validated environment;
4. `pyproject.toml` remains the **single source of truth** for new packages.

## 2. Scope and boundaries

- **In scope:** Python dependency management for `backend/` and the build/CI/Dev
  wiring that installs it; one pure-formatting fix and one `restore_db.sh` fix
  needed for the gates/verification to pass (items below).
- **Out of scope (unchanged):** application/trading logic, agent behaviour, DB
  schema, SAFE MODE semantics, Nginx, frontend (`npm`) dependencies, real-CA
  TLS/HSTS, git tags/releases, Phase 11.
- **Constraint honoured:** no broad upgrades. The locks **preserve exactly** the
  versions of the previously validated `backend/.venv` (verified: **0 version
  mismatches**). Drift in the OLD flow is documented in §10 to show the problem
  being solved, not re-introduced.
- **F-07 failure conditions avoided:** no `--force`, no bypass overrides, no
  arbitrary downgrades/upgrades were needed; the lock compiled cleanly.

## 3. Mechanism selected: pip-tools

| Tool | Decision |
|------|----------|
| **pip-tools 7.6.1** | **SELECTED** — smallest change vs the existing pip-based
  Docker/CI toolchain; standard hashed `requirements` files that plain `pip`
  verifies with `--require-hashes`; adds no runtime dependency to images (used
  offline, in a throwaway venv `/tmp/pt-venv`). |
| `uv` / `poetry` | Rejected — introduces a new package manager into Docker/CI,
  larger blast radius; `uv` lock is not what `pip --require-hashes` validates
  without extra tooling. |

`pip-compile` resolves the declared ranges from `backend/pyproject.toml`
(`[project] dependencies` = runtime closure; `[project.optional-dependencies]
dev` = dev closure) into fully pinned files with `--generate-hashes` and
`--strip-extras` (extras' dependencies become separate pinned lines, which is
required for `--require-hashes` compatibility).

## 4. Lock files produced

| File | Content | Pins | Hash lines |
|------|---------|------|------------|
| `backend/requirements.lock` | Runtime closure (what prod images install) | 56 | 1174 |
| `backend/requirements-dev.lock` | Runtime + dev (what CI/Makefile install) | 72 | 1518 |

Both are autogenerated by pip-compile (Python 3.12), fully hashed, with **zero
`# via` self-project pins** and **zero environment-marker lines** (the closure
is Windows-free and pure-`cp312` compatible for the images). No `.in` files
exist: `pyproject.toml` is the input.

## 5. Version-preservation proof (no unintended changes)

The locks were seeded from a `pip freeze` of the validated venv
(`/tmp/constraints.txt`, 91 pinned packages) passed to pip-compile with
`-c/--constraint`. Result (script-verified by canonical package name):

* **0 true version mismatches** between the validated venv and both lock files
  (runtime 56, dev 72).
* Pip-audit tooling (`pip-audit`, `cyclonedx-python-lib`, `requests`, …) is
  **not** in the locks by design — it is not a project dependency; CI installs
  it separately into the audit venv.
* Dev-only packages (`pytest`, `ruff`, `mypy`, `fakeredis`, `respx`,
  `freezegun`, `pandas-stubs`, `pytest-asyncio`, `pytest-cov`) appear in the
  dev lock only.

## 6. The one range change: pandas-stubs

The validated venv runs `pandas-stubs==3.0.5.260730`, but `pyproject.toml`
declared `pandas-stubs>=2.2,<3.0` — a **stale range that excludes the working
version**. pip-compile correctly refused to produce a lock. The declared range
was aligned to reality: `>=2.2,<4.0`. This is a **range alignment only** — the
lock still pins `3.0.5.260730`, exactly the installed version; nothing was
upgraded or downgraded.

## 7. Wiring — backend/Dockerfile

```
builder: COPY pyproject.toml requirements.lock ./ ; RUN pip install --require-hashes --prefix=/install -r requirements.lock && pip install --no-deps --prefix=/install .
dev:     COPY pyproject.toml requirements.lock ./ ; RUN pip install --require-hashes -r requirements.lock && pip install --no-deps .
```

* `--require-hashes` makes the build **fail** if any pin/hash is tampered with.
* The project itself is installed `--no-deps` (metadata-only wheel in builder;
  the real `app/` is copied in the runtime stages), so **nothing repulls
  dependencies from PyPI** at build time — the previous live-resolution drift is
  eliminated.
* `prod` stage is unchanged (copies `/install` from builder).

## 8. Wiring — Makefile

`make backend-venv` now:

```
python3 -m venv backend/.venv
pip install --upgrade pip
pip install --require-hashes -r backend/requirements-dev.lock
pip install --no-deps -e ./backend
```

(was `pip install -e './backend[dev]'`, which re-resolved live).

## 9. Wiring — CI (backend-ci.yml)

* `setup-python` `cache-dependency-path` now lists **both lock files** (pip
  cache keyed on the reproducible closure).
* `quality` and `integration` install steps: `pip install --require-hashes -r
  requirements-dev.lock` then `pip install --no-deps -e .`.
* The pip-audit job installs the **runtime** closure from
  `requirements.lock` with `--require-hashes` + `--no-deps -e .` before adding
  `pip-audit`, so the audited closure is byte-for-byte the locked one (STRICT
  policy unchanged, `docs/phase10-ci-security.md §2`).
* `docker-build.yml` needs no edit: the backend build context already includes
  the lock files; the Dockerfile consumes them.

## 10. The drift this eliminates (measured)

Before F-07, a fresh Docker builder pull resolved a **different** closure than
the validated venv: `alembic` 1.19.2 vs 1.19.1, `click` 8.5.0 vs 8.4.2,
`cryptography` 50.0.1 vs 50.0.0 — i.e. images, CI, and the host venv could each
"bless" a different set. After the lock, all three install the identical,
hash-locked closure.

## 11. Reproducibility verification (clean env)

Procedure: create a **fresh** venv; install exactly what CI/Makefile/Docker
will (`--require-hashes -r <lock>` then `--no-deps -e ./backend`).

Result (`/tmp/clean-venv`):
* `pip freeze` vs dev lock: **PERFECT — exact equality across all 72 packages**.
* Shared packages vs the validated venv: **identical**; the only difference is
  the (~19) pip-audit tool packages, which are not project deps.
* Sanity: `import fastapi, uvicorn, sqlalchemy, asyncpg, redis, pydantic,
  pandas, jwt` all succeed.

## 12. pip-audit (runtime closure)

Exact CI pattern replicated (`requirements.lock` + `--no-deps -e .` +
latest pip-audit + `--skip-editable`):
`No known vulnerabilities found` — **exit 0** (matches the STRICT policy).

## 15. Runtime verification (prod overlay)

Stack via `docker compose -f docker-compose.yml -f docker-compose.prod.yml`
(`target: prod` images):

* **12/12 services up, all healthy** (api, web, 5 workers, postgres, redis,
  prometheus, grafana, nginx); host ports **only :80/:443**.
* `/health/ready` → `{"status":"ok","mode":"safe"}` (200).
* `/system/status` → `app_env: prod`, `trading_mode: safe`, `safe_mode: true`.
* HTTPS: HTTP→HTTPS **301**, HTTP/2 200, TLSv1.2 and TLSv1.3
  (`TLS_AES_256_GCM_SHA384`), `CN=localhost`, security headers present
  (CSP/X-Frame-Options/X-Content-Type-Options/Referrer-Policy/Permissions-Policy;
  HSTS intentionally deferred to the real-CA phase, per `nginx.conf` staging note).
* WSS: register → login → ticket → `wss://localhost/api/v1/ws/stream?ticket=…`
  → subscribe ack `{"type":"subscribed","topics":["alerts"]}`. (Origin must be
  in the running `CORS_ORIGINS` allow list — §16.)
* **Backup/restore** (`backup_db.sh prod` + `restore_db.sh … prod`):
  1.47 MB dump, 18 tables, `alembic_version=0007` restored in an isolated temp
  DB, **matches live**, live DB untouched, temp DB dropped.
  * Note: `restore_db.sh` had a latent bug — the temp-DB name embeds a timestamp
    hyphen and the identifier was not quoted in `CREATE/DROP DATABASE`, so the
    script silently failed at creation (`2>/dev/null` hid it). Fixed by quoting
    the identifier; the manual pipeline had always worked, so previous "verified"
    reports exercised that path, not the script.

## 16. Residual notes

* **Regeneration procedure** (documented here so the lock stays current with
  intent, not accident): bump a range in `pyproject.toml`, then either re-compile
  against the existing venv to stay at current versions
  (`pip-compile --generate-hashes --strip-extras -c <venv-freeze> …`), or compile
  unconstrained to deliberately adopt newer versions. **Always** review the diff
  for unexpected upgrades before committing.
* **pip-audit itself** is still installed "latest" into its own CI venv (it is a
  scanner, not a shipped dependency); the audited **application closure** is the
  locked one.
* **WSS origin nuance:** the repo `.env` sets `CORS_ORIGINS=http://localhost:3000`
  which leaks into the prod overlay's `${CORS_ORIGINS:-https://localhost}`
  default; browser WS from `https://localhost` therefore needs an explicit
  `CORS_ORIGINS=https://localhost` at `make prod-up`. Deployment operators must
  set their own origin. (TLS/CORS policy owned by the TLS audit phase.)
